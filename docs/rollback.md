# 回滚手册 · 锚点

写这份手册的目的只有一个：出事的那天，照着它能一步步退回去，边看边做，不用回忆。

配套文档：`docs\release-v1.0.md`（发布清单）、`tools\export-snapshot.py`（数据快照导出）。

---

## 零、先分清两件事

**回滚只管代码**。把部署退回上一版，页面就能用了。它退的是 dist 那堆文件和云函数那包代码。

**数据被误删，回滚救不回来**。库里的行删了就是删了，退哪一版代码都变不回来。那时候只能拿发布前导出的快照重新灌进去，走本手册第四节。

所以备份和回滚是两件事，各练各的。这是最容易搞混的一条。

---

## 一、什么情况必须回滚（判断表）

先看这张表再动手，别一慌就退。

| 现象 | 是不是该回滚 | 该做什么 |
| --- | --- | --- |
| 公网打不开，显示 404 或 INVALID_HOST，本地同样的代码却是好的 | 是 | 回滚静态托管（第三节） |
| 页面能开，但接口报错、数据读不出来 | 不一定，先查 | 跑一次 `verify-project`，看 C13「代码字段与数据库对齐」。字段没加上就去控制台补 SQL，不是回滚的事 |
| 页面明显不对功能：按钮不见了、排版崩了、点了没反应 | 是 | 回滚静态托管 |
| 数据库被误删了记录 | 回滚没用 | 数据恢复（第四节） |
| 只是文案写错一个字、颜色不对 | 不是 | 改了重新传，别退版本 |
| 疑似密钥泄露（`_local\密钥` 里那把 API Key 流出去了） | 不是 | 去控制台作废重建 Key，再改环境变量。回滚版本解决不了密钥泄露 |
| 上线十分钟以内发现问题 | 是，立刻退 | 影响面还没铺开 |
| 已经跑了一整天，四五个人在用 | 先判断 | 先截图报错、查是哪一层坏了，确认是代码问题再退 |

**回滚的代价要算进去**：静态托管这条路 CloudBase 是「只建不更」，退回去得先删再建。中间公网会有一段打不开的空窗，实测 2 到 5 分钟。这段时间要是别人正好点链接，看到的是 404。

**退到哪一版**：v1.0 的上一版是 `部署包\4-前端dist(Day24-新建计划入口).zip`，源码对应提交 `7b343ff`。

## 二、回滚前先做三件事

1. **记下开始时间**。精确到分钟，写到本手册最后一节那个记录表里。没数字的演练等于没演练。
2. **确认退到哪一版，文件在不在**。现在是 `部署包\4-前端dist(Day24-新建计划入口).zip`。文件要是没了，从 git 取源码（`git checkout 7b343ff`）后用 `tools\build-dist.py` 重新构建。
3. **先截一张现在的报错图**。回滚之后现场就没了，回头要复盘只能靠这张图。

## 三、第一条路：静态托管回退（今天实操）

这条路由 Victor 亲手在控制台做，AI 在外面轮询公网状态并记录时间。

**第 1 步**　告诉旁边的人「我要开始回滚了」，顺便记下时间。这一句不是形式主义，是为了防止你在演练的时候别人正好往群里发链接。

**第 2 步**　打开 CloudBase 控制台 https://tcb.cloud.tencent.com/ ，确认左上角的环境是 `victor-1a2b3c4d-d5fmr5rn115087c8`。
该看到：环境名字后面跟着一串 journal ID。选错环境后面的操作全白做。

**第 3 步**　左侧菜单找「静态网站托管」。不同版本的控制台可能叫「静态存储」或放在「云托管」下面。
该看到：一个项目列表，里面有 `dist` 这一行，状态显示正常。

**第 4 步**　选中 dist 那一行，删除入口在这一行的「操作」列里，通常是下拉菜单或者一个删除图标。

控制台改过版的话，这里会遇到两种界面：一种是整个项目直接删；另一种要求先把里面的文件删空才能删项目。遇到后者就先点进项目，把文件全选删掉，再回来删项目。拿不准的时候把界面截个图，别硬点。

这一条是写手册的人已知的模糊点，同伴走查时如果也卡在这，说明得补一张界面截图进来。
该看到：确认弹窗。

**第 5 步**　确认删除，等它从列表里消失。
这时候公网应该已经打不开了。旁边的人可以试着刷新一下公网地址。
该看到：404，或者提示找不到页面。这是正常的，说明删除生效了。

**第 6 步**　点「新建部署」或者「上传」。
**项目名称必须填 `dist`，一个字母都不能差。**填成别的，地址就不是 `/dist/` 那一串了，跟原来对不上，以前的链接全废。
上传选 `部署包\4-前端dist(Day24-新建计划入口).zip`，zip 不用解压。

**第 7 步**　等部署完成，状态从「部署中」变成正常。通常一两分钟。

**第 8 步**　打开公网地址 https://victor-1a2b3c4d-d5fmr5rn115087c8-1499478684.tcloudbaseapp.com/dist/ 验证。第一次打开有腾讯测试域名的提醒页，点继续。

**怎么确认真的退回旧版了**（这是肉眼能分辨的差别）：

下面三条是从两份部署包里逐个文件比对出来的，不是凭印象写的：

| 看哪里 | v1.0 的样子 | 退回 Day24 之后的样子 |
| --- | --- | --- |
| 「去今日」按钮 | 在页头右上角那一块里 | 挪回左栏那张卡片里，跟着「接着做今天的那一项」那句话 |
| 记录台底部 | 有一条能折叠的回收站条 | 没有这条 |
| 右栏布局 | 拆成工具条和每天列表两张卡 | Day24 原来的样子 |

看到第 1 条就变了，才说明真的退回去了，不是缓存没刷。**刷新按 Ctrl+F5 强制刷新**，不然浏览器可能给你看缓存里的新版本。

补充一句，别被 DOM 骗了：两个版本的页面源码里都能找到回收站那个元素（`trashCard`），肉眼看得见的差别是它在哪一版里显示出来。所以判定以眼睛看到的为准，别去看源码里有几个字。

**第 9 步**　再验证数据没坏：
- 记录台里还能看到 2026-10-09 和 2026-10-10 两天的内容
- 或者直接打接口：`curl https://victor-1a2b3c4d-d5fmr5rn115087c8-1499478804.ap-shanghai.app.tcloudbase.com/api/plan-days`，返回里 `matched` 应该还是 2

**第 10 步**　记下恢复时间，算总耗时，写进最后一节的记录表。

## 四、第二条路：云函数回退（本次不实操，备查）

什么时候需要走这条：接口报错、health 接口挂了、数据读写异常，而且 `verify-project` 已经排除了数据库字段没加的情况。

**取旧代码有两条路**：
1. 部署包里有当时那份 zip（`部署包\plan-days.zip`、`checkins.zip`、`health.zip`），直接重传。
2. 没有 zip 就从 git 取源码：`git checkout 7b343ff -- cloudfunctions/`，然后跑 `python tools\pack-cloudfunctions.py` 重新打包。注意新打包的输出目录是 `部署包\`，别落成桌面。

**重传步骤**：控制台 → 云函数 → 选中那个函数 → 重新上传代码包 → 选刚才准备的 zip。
不用删除重建。重传会保留环境变量，TCB_ACCESS_TOKEN 不用重新配。只有主动删掉函数才会连环境变量一起删。

**验证**：
- `curl https://victor-1a2b3c4d-d5fmr5rn115087c8-1499478804.ap-shanghai.app.tcloudbase.com/api/health`，返回里要有 `"ok":true`
- 要是返回 `MISSING_TOKEN`，说明环境变量丢了，去函数配置里把 TCB_ACCESS_TOKEN 填上

**这次不实操的原因**：这条路的动作就是「重传一个代码包」，操作本身没有练的价值，风险也不在这一层。真正会让这个过程失败的只有两件事，旧的代码包找不着（已经在本节写清两条取回路径），环境变量被删（也写了怎么补）。相比之下静态托管那条路有删有建、有公网空窗期，才值得亲手练一遍。

## 五、第三条路：数据恢复（本次不实操，备查）

**先说一句硬话**：数据一旦被误删，回滚任何版本都救不回来。这条路只能靠发布前导出的快照。

**前提**：有快照。v1.0 的快照在 `_本地归档\2026-10-12-v1.0发布快照\`，里面有 `plan_days.json`、`checkins.json`、`manifest.json`。manifest 里记了行数和 sha256，恢复前先核对哈希，确认文件没被改过。

**发现数据被删之后的第一件事**：什么都别写。不要再点页面上的新建、保存，那些操作会往库里写新东西，把剩下的现场搅乱。先导出当前状态（`python tools\export-snapshot.py 另一个目录`），留一份「案发现场」，再动手恢复。

**恢复步骤**：

1. 打开快照 JSON，挑出需要恢复的那几行。
2. 用数据网关逐条写回去。地址是 `https://victor-1a2b3c4d-d5fmr5rn115087c8.api.tcloudbasegateway.com/v1/rdb/rest/plan_days`，方法是 POST，请求头带 `Authorization: Bearer <那把服务端 API Key>`。
3. 想一次写多行，就把 JSON 数组直接作为 POST 的请求体整个提交，网关支持批量插入。已经存在的日期会返回 409 冲突，那时候改用 PATCH 更新那一行。写入的确切字段清单看 `docs\api-contract.md`。
4. 两张表要分开灌：先 plan_days，再 checkins。顺序反了没影响，但别漏掉后一张。
5. 恢复完打开页面刷新，确认那两天的内容回来了。

**红线**：控制台 SQL 编辑器里能执行 SQL，但绝不能跑 `db\schema.sql`。那个脚本开头就是 DROP，会把整个库清空。要动结构就跑只加不改的脚本，比如 `db\软删除-加字段.sql`。

**这次不实操的原因**：恢复数据要先把导出的 JSON 灌回去，完整链路属于 Day 27「备份与恢复」的内容，今天如果把数据也练了，就越过当下的任务范围了。而且恢复过程一定会写入数据，在只有 2 行真实数据的库上演练，反而有把真实记录搞乱的风险。今天只保证一件事：快照存在 repo 里，且 manifest 的哈希对得上。

## 六、回滚后的验证方法（三条加一条）

不管走的是哪条路，回滚完必须过得掉这四条：

1. **公网能打开**。首页地址能出症状页面，不是 404，也不是 INVALID_HOST。
2. **读接口有数据**。打 `/api/plan-days`，返回的 `matched` 不该是 0。
3. **真实记录还在**。2026-10-09 和 2026-10-10 两天的内容都在页面上看得到。
4. **版本号对得上**。要是退回静态托管，页面上那三处差别（去今日的位置、回收站有没有、右栏布局）必须跟着变回来。没变说明退了个寂寞，多半是缓存。

**注意**：回滚态不要求 `verify-project` 13 项全过。旧版本来就没有页面整改和回收站，C12 那些针对新版写的检查会挂。这里的判定只看上面四条。
