## 四、发布方式

三样东西走三条路，别混。

**前端（静态托管）**：CloudBase 控制台 → 静态网站托管 → 删掉 `dist` 项目 → 同名重建，项目名必须填 `dist`，上传 `部署包\5-前端dist(回收站与页面整理).zip`。这个表单只建不更，同名会被拒，所以更新只能删了重建。

**云函数**：控制台 → 云函数 → 选中函数 → 重新上传代码包。不需要删掉重建，平台会保留环境变量（TCB_ACCESS_TOKEN 不用重配）。

**数据库结构变更**：控制台 → 数据库 → SQL 编辑器执行。红线是绝不能跑 `db\schema.sql`，那个脚本开头是 DROP，会把库清空。要加字段就跑 `db\软删除-加字段.sql` 这种只加不改的脚本。

**发布顺序**：先跑结构变更的 SQL → 再传云函数 → 最后重建前端。反过来会让页面先上去，一调接口就 500。

## 六、备份方式

**代码侧**：`git tag v1.0` 是主标记。配套三样：GitHub 远端 `github.com/gin996hhh/vibe-coding` 有完整源码历史；`部署包\` 里 5 份历史前端包是每一次上线时的原始产物，能直接拿来回退；云函数代码包同样在 `部署包\` 下。

这里有个容易踩空的点：因为 `dist/` 不进版本库，**推了仓库不等于备份了前端产物**。前端那份能直接上传的 zip 只存在于本地 `部署包\` 目录，所以要保住它，就得保住这个目录。云端另有一份副本，就是静态托管里正在跑的那个项目本身。

**数据侧**：`tools\export-snapshot.py` 走数据网关把两张表全量导成 JSON。v1.0 的快照在 `_本地归档\2026-10-12-v1.0发布快照\`，含 `plan_days.json`、`checkins.json`、`manifest.json`。manifest 里记了导出时间、每张表行数、日期范围、文件 sha256，将来灌回去之前可以先比对哈希。

v1.0 快照的实际读数：plan_days 2 行，checkins 2 行，日期范围 2026-10-09 到 2026-10-10，回收站内 0 行。

**为什么数据备份和回滚要分开**：回滚只管代码，把部署退回上一版。数据一旦被误删，回滚救不回来，只能靠快照重新灌进去。两件事各练各的。
